# Stage 7 — re-judge a stored run with edited questions — design

**Date:** 2026-09-24 · **Binding authority for Stage 7.** The plan that implements it is
`docs/superpowers/plans/2026-09-24-stage7-rejudge-plan.md`. Where this document and the parent design
(`2026-09-18-jevbrowser-design.md`) disagree, this one wins for Stage 7; the parent keeps §5.7, which
this document fills in.

## 1. What this stage is for

The whole reason the tool stores every answer whole (spec §5.7) is so questions can be changed and
asked again **without spending an eBay page load or a scrape**. Today a run can be re-opened and
re-weighted, and that is all: the questions are constants in `src/jev/questions.ts`, they cannot be
edited, and no run has ever carried more than one version.

**Deliverable:** reopen yesterday's run, change the wording of the questions, re-judge the same
stored listings, and see what changed answer by answer.

**Acceptance, as the build plan wrote it, kept verbatim:**

- re-judging a stored run makes no browser navigation at all (assert on the fake scraper's call count);
- a new questionnaire version is created;
- answers from the previous version remain readable and comparable.

## 2. What exists, and the three things that are not true

| Claim | Reality today |
|---|---|
| §5.7 "the questions used in each run are versioned" | `saveQuestionnaire` (called once, from `judgeSurvivors`) passes no version, so `version` is **always 1**. Nothing can be version 2. |
| §5.7 "the exact question definitions used" are stored | `definition_json` is `{ request, questionKeys }`. The **question text is not stored at all** — it lives in code, so a re-judge would have nothing to edit and no record of what was asked. |
| `listToJudge` selects what to judge | It selects `stage in ('survivor','detail_failed')`. After a first judging those rows are `'judged'`, so a re-judge built on it would find **nothing**. |

The version is also not optional for correctness: `judgments` rows carry `questionnaire_id`, but
`listJudgments` returns every judgment for the run and `score.ts`'s `answersOf` keys them by
`listingId`+`questionKey`. Two versions in one run would silently collapse into whichever row came
last, and the report would show a mixture of both.

## 3. Decisions

1. **A new questionnaire version, in the same run.** Listings, events and the run row are untouched;
   a re-judge appends one `questionnaires` row and its `judgments` rows. Rejected alternative: a new
   run copying the listings with `parent_run_id` — it duplicates listings and the whole event log,
   and the report, the export and the SSE stream are all already keyed on one run.
2. **The editable thing is a draft, and the prefix is not editable.** The draft holds the buyer's
   criteria and, per question, its body text and its anchors. The `About listing L3 — …` prefix and
   the pointer to the state are generated by code, so CLAUDE.md rule 16 ("a question must name its
   listing") holds by construction and no edit can break it.
3. **A question's kind is not editable.** `is_target_product`, `spec_match`, `condition_ok` and
   `criteria_freeform` stay noul; `listing_trust` and `price_value` stay score with five levels. The
   report's gates, weights and normalisation are written against exactly those six keys and those two
   shapes (rules 12, 12b); letting an edit change a kind would move the ground under `score.ts`
   without it knowing. Text and anchors only.
4. **Every version's judgments travel in one payload**, each carrying its `questionnaireId`; the
   browser filters. A `?questionnaire=` parameter was rejected because the row diff needs two
   versions at once, which would cost a request per version; the payload for a version is ~120 small
   objects, so carrying all of them is cheaper than carrying a cache.
5. **A half-finished re-judge is visible, not hidden.** No status column: a failed version simply has
   fewer judgments, so its listings show as `pending` in the report, and the reason arrives as a
   `rejudge.failed` event. CLAUDE.md rule 7 (silence is a bug) is about the page never lying.
6. **One job at a time still holds** (rule 9). A re-judge takes the same lock as a run: same JEV
   client, same SQLite file, one user.

## 4. Data model

No schema change. `questionnaires(run_id, definition_json, version, created_at)` and
`judgments(run_id, questionnaire_id, …)` already carry everything.

`definition_json` gains its missing half — the questions — and a pinned label map:

```jsonc
{
  "request": { "keyword": "…", "criteria_text": "…", "spec": {…}, "max_price": 1600, "accepted_conditions": […] },
  "questions": [
    { "key": "spec_match", "kind": "noul", "instructions": "Does this listing's …", "anchors": { "true": "…", "false": "…" } },
    { "key": "price_value", "kind": "score", "instructions": "How good is …", "levels": ["…", "…", "…", "…", "…"] }
  ],
  "labels": { "312": "L1", "313": "L2" },
  "questionKeys": ["is_target_product", "…"]
}
```

`labels` maps listing id → the label that listing was addressed by. It is stored rather than derived
because the diff compares two versions **per listing**, and a re-run's query order is not a contract.
`questionKeys` stays for readers written before this stage.

A questionnaire stored before this stage has no `questions` and no `labels`. It stays readable: its
judgments are untouched, and the editor starts from the shipped defaults (decision 4 of §5 below).

## 5. The draft and its builders — `src/jev/draft.ts` (new)

```ts
export type DraftQuestion =
  | { key: string; kind: 'noul'; instructions: string; anchors: { true: string; false: string } }
  | { key: string; kind: 'score'; instructions: string; levels: string[] }

export interface QuestionnaireDraft {
  request: SearchRequest
  questions: DraftQuestion[]
}

/** The six questions as shipped, body text only, ready to edit. */
export function defaultQuestions(): DraftQuestion[]

/** The draft a run starts from: the search's own request plus the shipped questions. */
export function defaultDraft(request: SearchRequest): QuestionnaireDraft

/** The stored draft of a version, or the defaults when it predates this stage. */
export function draftFromDefinition(definition: unknown, fallback: SearchRequest): QuestionnaireDraft

/** Why a draft cannot be judged. Empty array means it can. */
export function validateDraft(draft: QuestionnaireDraft): string[]

/** State and questions for one batch, from the draft rather than from the constants. */
export function buildFromDraft(draft: QuestionnaireDraft, listings: QuestionListing[]): Record<string, JevQuestion>
```

`buildFromDraft` is the draft's twin of `buildQuestions` and shares its prefix builder: same
`About listing L3 — "title" at $1,299.99: Its card, price, seller and item specifics are the state's
entry for L3.`, same `noul()`/`score()` SDK helpers, same label-from-position rule. `buildQuestions`
stays for the six shipped questions, and a test asserts the two agree when the draft is the default —
so the two can never drift into asking different things.

`validateDraft` rejects: fewer or more than the six known keys, a key whose `kind` differs from the
shipped one, a key repeated, empty or whitespace-only instruction text, an empty anchor, a score
question with fewer than 2 or more than 7 levels. Each rejection is a sentence the UI shows verbatim.

## 6. The pipeline

**`src/pipeline/judge.ts` gains a seam.** The batch loop — build state, call JEV, halve on a `422`,
store, publish — moves into:

```ts
export interface AskInBatchesOptions {
  client: JevClient
  batchSize: number
  emit: (type: RunEventType, payload: unknown) => void
  isCancelled?: () => boolean
  /** Which listings, already labelled in their run's order. */
  labelled: QuestionListing[]
  /** State and questions for one slice of them. */
  questionsFor: (batch: QuestionListing[]) => {
    state: ReturnType<typeof buildState>
    questions: Record<string, JevQuestion>
  }
  /** One batch's answers, by listing, stored by the caller. */
  onBatch: (results: { listing: QuestionListing; answers: Record<string, JevAnswer> }[]) => void
  /** Question keys to read back out of each answer map. */
  questionKeys: readonly string[]
}
export async function askInBatches(o: AskInBatchesOptions): Promise<JudgeOutcome>
```

`judgeSurvivors` keeps its behaviour (it selects `listToJudge`, saves under a new questionnaire, marks
each listing `judged`) and becomes a caller of `askInBatches`. `rejudgeRun` is the second caller:

```ts
export interface RejudgeOptions {
  db: SqliteDatabase
  runId: number
  draft: QuestionnaireDraft
  client: JevClient
  batchSize: number
  emit: (type: RunEventType, payload: unknown) => void
  isCancelled?: () => boolean
}
export async function rejudgeRun(o: RejudgeOptions): Promise<{ questionnaireId: number; version: number } & JudgeOutcome>
```

It: reads the run and its search; selects `listJudgeable` (**every listing whose stage is not
`'rejected'`**, in card order — see §2's third row); writes `questionnaires` version = max + 1 with the
definition above; judges with `buildFromDraft`; stores answers under that questionnaire id; and does
**not** touch `listing.stage` (a re-judge cannot make a listing more or less scraped than it is).

New event types on `RunEventType`: `rejudge.started {questionnaireId, version, listings}`,
`rejudge.finished {judged, costUsd, missingAnswers}`, `rejudge.failed {message}`. `judgments.received`
is reused unchanged, so a watching browser's existing listener already refreshes on each batch.

New storage helper in `src/storage/judgments.ts`:

```ts
export function nextQuestionnaireVersion(db: SqliteDatabase, runId: number): number  // max(version)+1, 1 when none
export function saveQuestionnaire(db, runId, definition, version): number  // version is now required, not defaulted
```

## 7. Server

**`POST /api/runs/:id/rejudge`**, body = the `QuestionnaireDraft`.

| Code | When | Body |
|---|---|---|
| 202 | accepted, judging in the background | `{ runId, questionnaireId, version }` |
| 400 | no such run; `validateDraft` returns reasons | `{ error, reasons? }` |
| 409 | a run or re-judge is already active | `{ error }` |

It returns immediately; answers arrive over the existing SSE stream. The route takes a
`judgeClientFactory` like `POST /api/runs` does, so the whole path is testable with a fake client and
no API key.

**`GET /api/runs/:id`** gains `questionnaires: [{ id, version, createdAt, definition }]` ordered by
version. `judgments` keeps its shape but every entry now carries `questionnaireId` (the storage type
already does; the web type does not yet).

## 8. UI

- **`web/src/lib/api.ts`** — `Judgment` gains `questionnaireId`; `Questionnaire` type added;
  `getRun` returns the questionnaires; `rejudge(runId, draft)` added.
- **`RunView.tsx`** — holds `questionnaireId` state, defaulting to the highest version. The report
  becomes `buildReport(survivors, judgments.filter((j) => j.questionnaireId === selected), settings)`,
  which is still a pure function of what the page has: switching version costs no request.
- **`VersionSelector.tsx`** (new) — a `<select>` of versions, showing `v1 · 12:31` style, above the
  report next to the export buttons. One version means no selector, so an ordinary run's header does
  not grow.
- **`AnswerDetail.tsx`** — takes an optional `previousAnswers` map and renders `was 0.62` beside each
  question that had an answer in the previous version, using the same formatters as the live answer so
  the two cannot read differently. A question with no previous answer says nothing.
- **`QuestionEditor.tsx`** (new) — prefilled from the selected version's definition: the buyer's
  criteria (criteria text, spec fields, budget, accepted conditions) and one block per question with
  its instruction text and its anchors or five levels. "Re-judge with these" POSTs and then lets the
  SSE events do the refreshing. Validation failures from `validateDraft` render under the form, and a
  409 says another job is running rather than pretending to start.
- **`export.ts`** — one new column, `questionnaire` (the version number), so a CSV file says which
  question set produced it.

## 9. Error handling

| Situation | What happens |
|---|---|
| No API key | The route builds the client before accepting, so it fails with 400 and a message, not a half-started job (the same reason `runner.ts` builds it before the first page load). |
| A batch is refused (`422`) | The existing halving, unchanged, per run (rule 17). |
| A batch fails for another reason | `rejudge.failed` is published and stored; the version stays partial; the report shows the unjudged listings as `pending`. |
| Cancelled | `askInBatches` stops between batches, `rejudge.finished` says `cancelled: true`, answers already stored stay. |
| A run with nothing judgeable | 400 with "this run has no listings to judge". |

| `scripts/repro-live-ui.ts` | the browser-level half: edit a question, re-judge, assert the fixture server saw **zero** requests during the re-judge, and print one listing's answer before and after. |

The four existing judge/run tests must keep passing untouched: a fresh run is the path that must not
change.

## 11. Out of scope

- Adding, removing or re-typing questions (§3 decision 3).
- Editing the search itself, or re-scraping any part of a stored run.
- Re-judging a single listing, or a subset other than "everything not rejected".
- Editing an old version in place. A new version is the only edit.

## 12. Open item carried forward

`spec: {}` on every stored search (recorded in the build plan) is **not** fixed here, but the editor is
where it would be fixed: the criteria half of the editor writes the draft's request, and the draft's
request is what the questions quote. Nothing in this stage writes it back to `searches`, so a fresh run
still starts from an empty spec. Doing that is a small follow-up on the editor, not a stage.
